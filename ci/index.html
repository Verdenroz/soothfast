CI#

soothfast in another repository is one step in the workflow you already have. On a pull request it gates performance against the base branch and comments the result. On a push to the default branch it records a measured reference for later pull requests, regenerates derived files, and lands them as a pull request authored by soothfast-bot, which merges itself once your checks pass.

Setup#

Two one-time settings, no secrets:

  1. Install the Soothfast Bot GitHub App on the repository. It asks for Contents and Pull requests write and Metadata read.
  2. Create an environment named soothfast-bot (Settings, Environments) with no deployment branch policy and no required reviewers. The job above runs on pull requests too, and a branch policy would fail every one of them, the bot's own included. The broker enforces the default-branch rule itself. The job that comments on a fork's pull request uses the environment too: with required reviewers it waits for an approval before every comment. A repository without the environment gets one from GitHub on the first run, with no protection rules.

Because the job names an environment, every run of it, pull request or push, appears under Environments and Deployments and on the pull request as "deployed to soothfast-bot". If you would rather keep pull requests out of the environment, split the step into two jobs with the same uses: line: the gate job on pull_request without an environment and with changelog: false, and a regeneration job on push with the environment. Leave gate on in the push job unless you want it to stop recording reference runs. That split lets you put a default-branch policy on the environment; its cost is that gate comments are then posted by github-actions rather than soothfast-bot, since only a job in the environment can obtain a bot token.

Two repository settings decide what happens to the bot's pull request:

  • If your default branch has a ruleset or branch protection with required checks, turn on "Allow auto-merge" so the bot can queue its PR behind them. Without rules the bot merges immediately.
  • "Automatically delete head branches" removes bot/soothfast-update after the merge. Without it the branch lingers until the next regeneration force-pushes it.

A ruleset that requires approving reviews applies to the bot too: its PR waits for a human.

Setting up and pinning#

cargo soothfast init writes the workflow, soothfast.toml and the .gitignore entry for any repository. A repository with no Cargo manifest is set up from the Gradle, Maven, Python and Node projects it tracks, as [[project]] tables; the Rust-only steps are skipped.

A repository pins soothfast in several places that must agree: the soothfast* requirements in Cargo.toml and their entries in Cargo.lock, the uses: <owner>/soothfast...@<sha> # vX.Y.Z refs in its workflows, a soothfast_ref input, and a literal cargo install cargo-soothfast --version X.Y.Z. cargo soothfast bump [--to VERSION] moves all of them to one release, the running CLI's own unless --to says otherwise. It resolves each tag to its commit with git ls-remote, keeps the version comment in step with the SHA, updates Cargo.lock for just the packages it moved, and prints one line per file it changed. A requirement the release already satisfies, such as "0.5" against 0.5.7, is left as written.

cargo soothfast bump --check writes nothing and needs no network. It prints file:line found X, want Y for each stale pin and exits 1 when there is one, so it can gate a pull request. A line that names cargo-soothfast with a version it cannot read is printed as unrecognised and does not fail the check.

Checking the setup#

cargo soothfast status prints what state the setup is in, from what is already on disk and in git. It builds, measures and fetches nothing. Each line is a state word (ok, stale, failed or missing), the subject and, unless it is ok, the command that addresses it:

The checks cover the CLI against the soothfast version Cargo.lock pins, the last gate verdict and its triage, soothfast.lock once markdown carries bind markers, the files init writes against what init --check would report, and the last test run. The init check reads without the network, so a release pin that is not already in the workflow reads as the tag. Its row is missing when the workflow is absent and stale with the drifted file names otherwise. The test row is failed, stale when the last pass was on a different tree, or missing when no run is recorded. Gate runs and baselines that are not recorded locally read as ok, since CI measures them; --all shows which. --all lists the ok lines instead of counting them, and --json prints the rows as an array of state, subject, detail and fix. The exit code is 0 when every row is ok and 1 otherwise. A failed gate points at its triage file; accepting a regression stays a decision for a reviewer.

What the step does#

Every run installs cargo-soothfast pinned to the soothfast version in your Cargo.lock, cached across runs. The binary is downloaded from the GitHub release and checked against its SHA256SUMS; if that fails the step warns and falls back to cargo-binstall. Pin the action to a release no newer than that version: the scripts pass flags the CLI at the action's ref understands. Runs that have nothing to do (a push to another branch, a pull request with gate: false) stop there. Otherwise the checkout is unshallowed so merge-base and tag lookups work.

On pull_request. It runs cargo soothfast ci gate, which gates each package (see packages below) against the pull request's base commit, and posts the output as one comment on the pull request, updated in place on later pushes. The comment shows the last forty lines per package. On a regression it uploads .soothfast/triage/ as the soothfast-triage artifact and fails the step. The comment is posted as soothfast-bot by the broker itself: the job sends the text over its OIDC identity and never holds a token, so a pull request branch, which runs code nobody has merged, cannot borrow the bot for anything else. A pull request from a fork has no OIDC identity; there the comment falls back to github.token (github-actions), or is skipped with a warning where that token is read-only, and the gate result still decides the step.

On a push to the default branch. With gate: true it first runs cargo soothfast ci gate, which gates each package against HEAD^ and stores HEAD's run in .soothfast/runs/ so the next pull request whose merge-base is this commit, or builds the same bench binary, reuses it instead of measuring its merge-base in a worktree. A regression or an error here is a warning: the code is already merged, and the steps after it still run. There is no comment and no triage upload. Recording needs two things from your workflow: a cache step for .soothfast/runs/ that wraps this job on pushes as well as on pull requests (see Reusing a measured reference), and .soothfast/ in .gitignore, since a run is stored under its commit only from a clean tree. With cargo-soothfast 0.3.2 or earlier in your Cargo.lock, a push whose bench binary matches its parent's records nothing unless a run for that binary is already stored. Pushes by soothfast-bot can skip the job: they leave the bench binary alone, so a pull request based on one finds the previous commit's run by binary.

Then it measures each package into the baseline baseline, regenerates CHANGELOG.md against the latest tag (or lists the initial surface when there is no tag), regenerates any packages named in spec, records fresh output for each capture block, and lands whatever changed as one pull request on bot/soothfast-update. Pushes to other branches do nothing beyond the install.

The bot PR triggers your workflows like any other pull request, this step included, which is how its required checks get satisfied. Under run.yml the plan recognises the landing and runs no lane for it; see Bot landings. Jobs that skip on a [bot] actor count as passed for required checks. If the bot PR is left open, your ruleset gave auto-merge nothing to wait on (a pull request rule with zero required approvals and no required checks); merge it by hand or drop the rule.

One landing per commit#

Jobs that land files for the same default-branch commit add to one branch, bot/soothfast-update, and one pull request, so jobs that finish close together cost the default branch one bot commit. A job joins only while the landing is open: the pull request merges as soon as its required checks pass, and a job that finishes after that starts a second landing on the new tip. A job of your own joins by running action/land.sh with TOKEN, APP_SLUG, TITLE and PATHS and leaving BRANCH unset. The script adds its commit on top of the bot's commits already on the branch, and starts the branch over from the default branch's tip when it is missing, based on an older commit, or holds a commit that is not the bot's.

The pull request keeps the title of the job that opened it. Its body lists one line per job, its TITLE and the files it landed (the first ten, then a count), and running a job again replaces its own line, found by its TITLE, so two jobs must not share one. A job that finds its files already on the branch changes nothing. BODY, when set, opens the body of a landing the job starts.

A job that sets its own BRANCH keeps a separate pull request on that branch.

Why the environment#

The step needs id-token: write to prove its identity to the broker. That permission is also common on jobs that publish to crates.io, PyPI, or a cloud provider over OIDC. Requiring the soothfast-bot environment means only a job that opts in can obtain a bot token; a compromised action in one of those other jobs cannot. The broker hands out one kind of token, scoped to your repository for one hour and revoked when the step finishes: a landing token (contents and pull requests write) for push, workflow_dispatch, or schedule runs on your default branch, or on a tag whose commit is already on it. A pull_request run from the repository itself gets no token at all; it asks the broker to post the gate comment, and the broker does so with a token it holds and revokes itself. The broker takes the same request from a workflow_run job on the default branch, for a fork's pull request only. That job gets no token either, and the broker posts only after it finds the named pull request open, from a fork and not this repository, and still at the head commit the job names (and, with the optional Actions permission, after it verifies the run too; see Pull requests from forks). Every other event, ref, or repository the App is not installed on is refused.

Rustdoc cache#

spec and docs commands build rustdoc JSON, which compiles the package and its dependencies under nightly. With rustdoc-cache: "true" the job keeps .soothfast/rustdoc between runs, and a command that finds the JSON it needs there skips cargo entirely. The reusable run.yml keeps it for its docs check, and for the changelog regeneration on a default-branch push. Set [docs] package in soothfast.toml and a docs command run without -p reads that package.

Lookup has two levels. A key hashes the package, features, visibility, the rustc -vV of the rustdoc toolchain, the rustdoc format version, every RUSTFLAGS, RUSTDOCFLAGS, CARGO_ENCODED_*, CARGO_BUILD_*, CARGO_PROFILE_* and CARGO_TARGET_* variable (bar the target directory and job count), Cargo.lock, the root manifest and cargo config, and the content of every file git lists in the package and its path dependencies, apart from .github and .soothfast. Uncommitted edits count, and a nested repository or submodule is hashed through. The key selects a manifest of the other files the last build read (from rustdoc's and cargo's dep-info and the build scripts' rerun-if-changed) and the variables it depends on (env-dep lines and rerun-if-env-changed). The entry is named for the key and a hash of those, so a changed include_str! target outside the package, or a changed build script input, is a miss. The merge-base checkout hashes the same way, so JSON a default-branch push saved is the base side of a pull request's docs diff.

A result is stored only if nothing it read changed during the build.

Not covered:

  • What a build script reads without declaring it, and variables outside the families above that it does not name in rerun-if-env-changed.
  • Cargo configuration outside the repository, such as ~/.cargo/config.toml, and variables such as RUSTC_WRAPPER.
  • Absolute paths rustdoc records for sources outside the workspace.
  • A package whose sources sit outside the repository, or a tree without git, has no key and is always rebuilt.

The key has a second, stable half: the same head and variables, with only the files that configure the build (Cargo.toml, Cargo.lock, build.rs, cargo config and toolchain files, wherever git lists them). When the full key misses, the last entry stored under the same stable half is checked against its manifest. If every file and variable the build read still holds, it is a hit and is kept under the current key too. So a file the build never read (a lock file, CHANGELOG.md, a generated spec or SDK) does not cost a rebuild, even for a package at the repository root, where the full key covers the whole repository. A file the build read, or a changed configuration file, is still a miss. This trusts dep-info and rerun-if-changed lines to list what a build reads, as cargo does. An entry whose build script names nothing to watch, or whose dep-info could not all be read, is found only by its full key. Each stable half points at the entry built last: cache merge keeps the pointer of whichever side built later, and an exact hit repoints it.

Caches are kept per job, runner OS and architecture, and cache-suffix, and the rustdoc store is capped at 1 GiB, dropping the least recently used entries first. The action saves through actions/cache, which saves a new entry at the end of every job that did not hit its exact key, even when nothing was added. A composite action has no end-of-job step to compare against, so that cost is accepted. Set SOOTHFAST_TIMINGS=1 to print how long each rustdoc build, parse and cargo bench took.

Bench executable cache#

A job that gates, or runs spec check, builds its bench executable from cold: cargo bench --no-run for the gate's HEAD side, and a dev-profile build for the route listing behind spec check. A change that leaves the sources alone, a docs-only pull request, yields the same bytes, and the build dominates the job. bin-cache keeps .soothfast/bins between runs; a job that finds its executable there builds nothing, and the gate runs the stored file directly. It gets the package directory as its working directory, as cargo bench gives it, and the variables CARGO_MANIFEST_DIR and CARGO_PKG_NAME. Other CARGO_* variables and LD_LIBRARY_PATH are not set. A tree with a configured cargo runner (a runner key in the repository's or CARGO_HOME's config, or a CARGO_TARGET_*_RUNNER variable) is never served from the store, since the runner is part of what is measured.

The key and the manifest are built as for the rustdoc cache, over the package, bench target, profile, features, codegen-units pin, toolchain, rustc -vV and the same variable families, with two additions: RUSTC, RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER, RUSTUP_TOOLCHAIN and CARGO_INCREMENTAL join the variables, and the manifest comes from the dep-info cargo writes for the bench executable and every workspace dependency plus the build scripts' rerun-if-* lines. An entry is kept only if every dependency's dep-info could be read.

Markdown files are left out of the key's file list, so a docs-only change is a hit even for a package at the repository root, where that list is the whole repository. A markdown file the build included (include_str! on a README, say) is in the manifest and counts. The stable half of the key works as it does for rustdoc JSON.

The checkout path is part of the key, and so are the target directory and CARGO_HOME. A binary can carry them: env!("CARGO_MANIFEST_DIR"), file!(), OUT_DIR and debug info all write absolute paths into its bytes, and the run cache, item cache and link maps all key on those bytes. Two checkouts of one tree at different paths gave identical executables only while no such path was compiled in. A job that moves its checkout between runs misses; CI runners use one path per repository.

Each entry also keeps the digest of its binary and its link map, written once the first run has worked them out. A hit reads the digest instead of computing it, and puts the map back under .soothfast/maps if that was pruned. A map found nowhere is made by linking the bench target again, which on a cold target directory means a full build, once: the map is then kept in the entry for the runs after it.

The store holds one executable per checkout, target directory, package, bench target, features and profile: a newer one replaces the older, so a saved cache is the binary the branch runs and not its history. The merge-base worktree builds elsewhere and so has its own. cache merge keeps the newest of each group by the time it was made, and pruning by size removes whole entries, oldest payload first.

Cache budget#

A saved entry is as large as the executable, tens of MB, and GitHub keeps about 10 GB of cache per repository, evicting the least recently used. An entry that displaced the measured-run caches would cost more than it saves, so the action is conservative:

  • bin-cache is off by default. Turn it on for the job that builds the bench target through the action (gate: "true", the default).
  • The executables are restored before the gate and saved after it, in a step of their own, only if a listing of the store (names and sizes, not times) differs from the one taken before the gate. A job that hit its executable, such as a docs-only pull request, saves nothing.
  • A job outside the action, such as a spec check step in the adopter's own workflow, restores and saves .soothfast/bins with actions/cache on a key of its choosing. Key it per job and runner like rustdoc-cache, and save it with actions/cache/save guarded the same way, or only on the default branch.

Not covered, beyond what the rustdoc cache lists: a markdown file a proc macro or build script reads without saying so, the linker and C compiler a build script invokes, and anything a bench reads at run time besides its working directory and CARGO_MANIFEST_DIR. The store keeps 512 MiB at most.

Labels#

soothfast-bot acts on pull request labels the moment they change. GitHub delivers the App's webhooks to the broker, which reads [bot] from soothfast.toml on the default branch (never the pull request's copy) and acts as soothfast-bot:

LabelEffect
soothfast:mergeEnable auto-merge behind the required checks, when a writer applies the label. Refused when the default branch requires no status check, since the merge would happen at once.
soothfast:updateMerge the default branch into a pull request that fell behind, when the update is needed (see update below).
do-not-mergeCancel a queued auto-merge and leave the pull request alone.

A label counts only when the person who last applied it can write to the repository, so neither a fork nor the Triage role can merge a pull request through soothfast-bot. do-not-merge counts from anyone, since it only holds a merge back. Drafts and pull requests that already have auto-merge enabled are skipped, and the broker logs why. A pull request GitHub would already merge (every required check passed or was skipped, which path-filtered checks make common) cannot queue auto-merge, so the bot merges it at once, bound to the labelled commit and the configured merge_method. GitHub turns auto-merge off when someone without write access pushes to the branch, so later pushes and sweeps never turn it back on: to queue the merge again, remove soothfast:merge and add it back. The merge is tied to the commit the label was applied to: if the branch moves or the label comes off before the bot acts, it neither queues nor merges anything. The bot never watches statuses; GitHub's auto-merge, rulesets and merge queue decide when the merge happens.

A pull request gate labelled soothfast:perf-accepted reports its regressions in the comment and passes; label the pull request, then re-run the failed gate. The label waives regressions only, never a gate that errored, and it needs a writer too. perf_accepted_labels renames it, and the gate reads that list from soothfast.toml on the pull request's base branch, never the pull request's copy: a pull request that could rename the waiver to a label a maintainer applied for another reason would waive its own regressions. When the base branch's table cannot be read (an older cargo soothfast, no file there, a malformed table), the gate warns and accepts only soothfast:perf-accepted.

Configuration#

The broker acts only on a [bot] table with labels = true in soothfast.toml; repositories without it are left alone. cargo soothfast init turns the bot on: it writes the table, writes the reconcile job and creates the labels with gh; if gh cannot, init warns and cargo soothfast init --labels creates them later. --no-labels skips those three, and --no-bot skips the bot altogether (no schedule, no labels job, no changelog regeneration).

Two one-time steps remain: install the soothfast-bot App on the repository, and let the first run create the soothfast-bot environment. Until the App is installed the broker refuses to mint a token; the action warns and lands nothing as the bot instead of failing the job.

cargo soothfast init --labels (implied by --bot) creates each label with the colour and description of the [[bot.label]] entry that names it, else a default for its role. A bad colour fails --labels and only warns when --bot implied it; an entry naming a label no role uses warns. The broker ignores [[bot.label]]. cargo soothfast labels [--ref REF] [--role ROLE] prints the configured names.

update_all = true brings every open, non-draft pull request against the default branch up to date on each push to it, as if each carried an update label. An ignore label (do-not-merge by default) still opts one out. It needs no writer to apply anything, because the setting is read from the default branch. Each push evaluates as many pull requests as the Workers subrequest budget allows, least recently updated first, so successive pushes reach every open pull request.

landing_paths and slug decide which pull requests count as the bot's own landings; see Bot landings. The broker checks their types and reads neither. A broker deployed before it knew the two keys treats them as unknown, so deploy the broker first when you run your own; with the hosted broker, set them once it has been deployed at or after this change.

Every update restarts the pull request's checks, so by default (update = "needed") the broker updates a pull request that is behind or diverged only for one of two reasons:

  • The default branch requires branches to be up to date before merging (a ruleset's or classic protection's "require branches to be up to date"). A merge queue does not count. Classic protection with required checks counts unless it says strict: false, because GitHub does not always report the flag. When the rules or protection cannot be read, the broker assumes the branch is strict, since a pull request nobody updates could never merge.
  • The commits arriving from the default branch and the pull request's own commits change a common file, so a semantic conflict is tested before merge. This is a file-level approximation. When either file list may be cut short (GitHub's compare lists at most 300 files) the broker assumes an overlap.

When neither holds the broker logs why it did not update and leaves the pull request on its existing checks, so on a branch with no up-to-date requirement a labelled pull request may stay behind the default branch and still merge; that is not a bot failure. Under a strict default branch each update invalidates every other pull request, so a sweep updates at most one per run: pull requests with auto-merge enabled first, then the least recently updated. Pull requests that are already current do not count, so the next sweep moves on. Updates for an overlap are not limited, and a webhook for a single pull request is never limited. update = "always" updates every pull request that wants it and is behind, on every push to the default branch. update_all keeps its meaning and follows the same update setting.

A broker deployed before it knew update treats a table that sets it as malformed and acts on nothing, so deploy a self-run broker before adding the key to soothfast.toml.

A malformed [bot] table (an unknown key, a wrong type, a duplicate) makes the bot act on nothing and log why. Deleting the head branch stays the repository's "Automatically delete head branches" setting.

Operator steps#

Once per broker deployment (see bot/):

  1. In the App's settings, set the webhook URL to https://<worker>/webhook, choose a secret, and subscribe to the Pull request and Push events.
  2. Store the same secret in the Worker: `wrangler secret put GITHUB_WEBHOOK_SECRET. Without it/webhook` answers 500.
  3. The App needs Contents write, Pull requests write and Metadata read. Actions: Read-only is optional; it lets the broker verify the run a fork's verdict came from. Add it under the App's Permissions and events; until each installation accepts the new permission the broker keeps working without it.

Reconciling missed deliveries#

GitHub does not redeliver a webhook that failed. On default-branch pushes and schedules the action asks the broker to sweep the open pull requests: it cancels queued merges held by do-not-merge, updates labelled branches and closes conflicting landings, but never enables a merge. labels defaults to "true"; set labels: "false" to turn the sweep off, as the workflows init writes do for every job but the labels job.

A landing that conflicts with the default branch can never merge, and nothing else rebuilds it, so the sweep closes it. It does this only for a pull request opened by the App's own <slug>[bot] login from a bot/ branch of the repository itself, and only when GitHub reports it as conflicting for the head the sweep listed. A state GitHub has not computed yet is left for the next sweep, and so is a landing carrying an ignore label such as do-not-merge. The branch is left as it is: the next job that has something to land starts it over from the new tip and opens a fresh landing.

The sweep is best effort, since webhooks are the primary path, and it never fails the job: a missing jq, a job without id-token: write and environment: soothfast-bot, or a bot-token leaves a notice, and an unreachable or refusing broker leaves a warning with the broker's reason.

Limits#

  • Only pull requests into the default branch are evaluated. For one retargeted onto it, the next sweep handles its update label; apply soothfast:merge again to queue it.
  • A push or sweep stops starting pull requests when its remaining Workers subrequest budget cannot cover another, taking the least recently updated first among those the bot could act on. The broker logs when it truncates.
  • The broker caches each repository's soothfast.toml for up to 60 seconds per Worker instance, so a changed [bot] table can take that long to apply. A push to the default branch that changes the file, or whose commit list cannot show whether it did, drops the cache first.
  • A pull request that is already mergeable on a merge-queue branch is not enqueued: GitHub refuses the direct merge, and the broker logs it. Apply soothfast:merge before its checks finish.
  • A pull request whose only failing checks are not required is merged at once, the same as native auto-merge, which waits for required checks only.
  • Branch protection that the App cannot read counts as no required checks, so soothfast:merge is refused rather than risk an immediate merge.
  • On a merge-queue branch the bot relies on GitHub's auto-merge to enqueue the pull request; this has not been exercised against a live queue.

With bot-token there is no broker, so the label sweep leaves a notice and does nothing; only a broker, hosted or self-hosted, acts on labels.

Bringing your own token#

If you would rather not depend on the broker, install your own GitHub App with Contents write, Pull requests write, and Metadata read, mint an installation token in an earlier step (for example with actions/create-github-app-token), and pass it as bot-token with the App's slug as bot-slug. The id-token: write permission and the environment are then unnecessary.

Self-hosted runners#

A runner that only has git, bash, curl, docker and the runner agent can run the reusable run.yml workflow (see importing) if it provides the following.

Every job:

  • git, curl, bash, sed, awk and grep. The install step fails naming git or curl when either is missing.
  • Network access to github.com, crates.io, and the services the pinned actions download from (the Java, Node and uv setup actions fetch their toolchains).
  • cargo is set up for you with dtolnay/rust-toolchain (stable) when it is not on PATH, because cargo soothfast is a cargo subcommand. That needs the network and a C compiler and linker (cc) to build a Rust project. cargo-soothfast itself is installed from crates.io when the workflow's ref is a published release, else built from the ref into $RUNNER_TOOL_CACHE/soothfast-cli/<commit>, cached by commit and linked into $CARGO_HOME/bin. The first build of a ref takes several minutes.

Jobs that run the composite action (the cargo gate and the labels job). A plain pull request gate needs cargo and one of jq or gh (to read the default branch). The rest is needed only by the step that uses it, and each fails naming the tool:

  • gh, to comment with the job token and to land regenerated files. Without it the gate still runs and only skips the perf-accepted label check, with a warning.
  • jq, to comment, sweep labels or mint a token as soothfast-bot, to land regenerated files, and to find the bench packages when none are named.
  • valgrind, for the callgrind fallback on machines without hardware performance counters. The step installs it with apt-get when it runs as root or passwordless sudo is available, and otherwise warns and carries on. A runner with performance counters does not need it.
  • rustup, for a nightly or pinned rustdoc toolchain. dtolnay/rust-toolchain installs it when it is missing.

Per-project gate jobs:

  • Java for Gradle and Maven projects, Node for Node projects and uv for Python projects come from actions/setup-java, actions/setup-node and astral-sh/setup-uv, so the runner needs nothing preinstalled. A Gradle project's own ./gradlew downloads Gradle, and Python itself comes from uv.
  • Gradle and Maven dependencies, and the Gradle wrapper, are cached by actions/setup-java, keyed on the project's build files.

step-security/harden-runner is the first step of every job; it targets hosted runners and its network audit may not apply on yours.

One build#

Every job that gates, checks docs or runs spec commands used to compile for itself on a cold runner, and many of them compiled the same crates in parallel. run.yml now compiles once. After plan, two build jobs run on separate machines: Build (bench) and Build (rustdoc). The gate waits for the first only, so it never waits for a nightly rustdoc build. The docs check waits for the second and for the gate, since it reads the gate's baseline. On a pull request whose gate is not split into shards, the gate runs in the bench build's own job, named Build and gate, straight after the build: it needs no write token there, and a job of its own would set up a second runner only to read what the first just built. When the docs bind no Rust item, docs check builds no rustdoc, so neither Build (rustdoc) nor a nightly toolchain runs at all.

LaneBuildsInto
benchHEAD's bench executable of each gated package, its link map, and the merge-base's executable and map when the run cache holds no run for the merge-base.soothfast/bins
routesThe dev-profile executable behind spec check, for each package with a [[spec]] entry.soothfast/bins
rustdocRustdoc JSON for the docs package and, for each package that generates a spec, for it and the workspace crates its types come from.soothfast/rustdoc

run.yml builds the bench and rustdoc lanes. Its spec check job builds what it needs itself, so run.yml builds no routes lane. A job is skipped when its lane has nothing to build, and each lane reads its store first and builds only what is missing. The bench lane leaves the merge-base alone for the reason the gate does: if the run cache holds a run for it, the gate reuses that run and never builds the executable. That run is keyed by the CPU model, so a leg on a different one finds none and builds the merge-base itself: a miss, not a wrong answer. When a HEAD bench executable fails to build the merge-base side is not built, and a rustdoc or routes failure does not stop it. A workspace crate whose rustdoc fails to build for a generated spec is reported and dropped, as spec gen does. Each lane prints what it built against what it found, and SOOTHFAST_TIMINGS=1 times every build.

Each job uploads soothfast-store-bench or soothfast-store-rustdoc as a tar (an artifact drops file modes, a tar keeps them), kept one day. They hold only the entries the lane built or found (prebuild-stage): the executables with their digests and link-map extents, and the rustdoc JSON, not the rest of a restored cache. The Rust gate, every shard of it, downloads the bench artifact into .soothfast/ and the docs check the rustdoc artifact, and each finds a hit for everything it reads and compiles nothing. The tests, and the gates and tests of the other ecosystems, do not wait for either build.

A job that runs when its build job failed finds nothing to download and compiles for itself, so a compile error still shows up in that job's output and in the verdict. The docs job also keeps the Rustdoc cache as a fallback, so a store that misses costs no more than before.

A hit needs the reading job to be the same machine setup as the building one. The key names the checkout path, the target directory, CARGO_HOME, rustc -vV and the build variables (RUSTFLAGS, CARGO_INCREMENTAL, and the CARGO_PROFILE_, CARGO_BUILD_ and CARGO_TARGET_ families). The path cannot be made relative: compiled code carries it, so a binary built at another path is not the same binary. GitHub-hosted runners use one workspace path per repository for every job. The reading jobs set up the toolchain and rust-cache the way the build jobs do, since those steps export some of the variables. A runner pool with a path per job misses every time, and the jobs then compile as before.

Sharding#

shard: 3 on the run.yml call splits the Rust gate into three legs, each gating the items its I/N shard owns. Each leg reads the prebuilt executables of both sides, so measuring is all it does:

The legs record soothfast-result-rust-shard-<i>-of-<n> and the verdict folds them into one section for the package. Each leg of a pull request saves the items its shard owns into its own head baseline, stamped with the shard and listing every item the bench binary holds, and uploads it as soothfast-baseline-rust-shard-<i>-of-<n>. The docs job builds one baseline from exactly the files of this run with cargo soothfast baseline merge --into head --expect N --packages "A B" FILE.... A package whose gate failed or errored, sharded or not, saves no numbers and lists the items its shard owns as gate-failed; a leg that wrote no file at all leaves its shard's items shard-missing, named from the other legs' listings. A corrupt file, or one from a gate split another way, fails the docs job after binds and examples are checked. A default-branch push records every item in its first leg and saves the baseline as before; the other legs are skipped on a push, since they would only set up. A push whose commit has no parent lists its items as no-parent.

The docs check runs with --against-ref on the merge-base: a claim reads "not evaluated" only when the merge-base made it unchanged and its metric is listed unmeasured. A new or edited claim, or one on an item nothing lists, fails without a measurement. Counters taken from the item cache, from a run stored for the same binary or from a run-cache hit on HEAD count as this pull request's, since the code they measured is proven identical; walltime from those sources does not. A pull request whose bench binaries match the merge-base, with no stored run of them, reports its counter claims not evaluated, since its gate takes no counters. The cargo gate measures only a pull request and a default-branch push. On any other event (a push to another branch, a tag, workflow_dispatch, merge_group) the merge writes one not-gated-on-event entry: every claim whose item does not start with a configured import prefix (each [[project]]'s prefix, else its format's) is not evaluated. Imported claims measured on that event are checked as usual, and a missing or misspelled imported id fails. A prefix equal to a package name in the cargo workspace (- read as _), the only name a Rust id starts with, fails import, gate --import, and a baseline merge of an import file or an ungated event; with no workspace to read, a note says the prefixes went unchecked. A merge of Rust shards alone never reads soothfast.toml. Where no measurement was possible (not-gated-on-event, no-parent), a claim reads "not evaluated" even when it is new or edited.

Which items belong to which package comes from each package's bench binary listing, recorded as owners in the baseline, never from an id's name: every bench file's ids start with the bench target's name. An entry covers only the ids it names. A failed package's old numbers are exactly the ids it owned and no other package owns, and its entry names those, or the ones its listing shows; with neither it names nothing, and a claim on an item no package owns fails, naming that gate failure as possibly related. A leg that uploaded nothing at all, from a setup failure or a cancel, gets a no-measurement entry naming the items the Build (bench) job listed for its package from the stores it built, with cargo soothfast baseline plan (the soothfast-plan artifact, passed to the merge as --plan): an unchanged claim on them is not evaluated and a new or edited one fails. An item no listing names, an import's among them, still fails. An id two packages both list, as a lib item linked into both their bench binaries is, belongs to both, and a claim on it reads the number the last save wrote. A full save leaves alone any id another package owns. baseline merge refuses an id two merged files both hold.

--save-baseline, on gate or measure, needs -p in a workspace with more than one bench package, and fails before measuring without it; with one bench package the save is that package's. A filtered save updates the package's numbers in place, and a failed filtered gate drops and names only the filtered ids. A full save into a baseline saved before owners existed replaces every bench item no other package owns, and says to re-save the other packages. Baselines saved before owners existed are read with their old unmeasured entries left out, and the check says to re-save them.

cargo soothfast prebuild runs the same lanes by hand: -p PKG for bench packages, --against-ref REF for the merge-base, --docs PKG, --spec PKG[:TARGET], --only bench|routes|rustdoc, --stage DIR and --shards N.

A spec job of the caller's builds its own lane with the action: prebuild: routes rustdoc runs those lanes in place of the gate, for the packages with [[spec]] entries, and prebuild-docs: PKG alone runs rustdoc. A later job downloads the staged directory into .soothfast/ before spec check.

Checks from the file#

cargo soothfast plan also reads what else soothfast.toml configures and gives run.yml one job for each: ci spec for every package with a [[spec]] entry, ci proto for every package with a [[proto]] entry, ci coverage for every workspace member with a library target, ci capture for every docs package with docs of its own, and ci site when the file has a [site] table. A job is named for its record, spec-PKG or site, runs cargo soothfast ci KIND -p PKG, and installs the pinned rustdoc toolchain when its command reads rustdoc JSON (spec, coverage and site). The verdict expects a result from each. A kind named in [ci] skip gets no job.

A finding of ci spec (spec gate found a consumer-breaking change, or spec check found a spec that no longer matches its routes) is advisory: the job exits 0, its output is in the log and the comment, and the section reads advisory. A command that could not run still fails, and so does a stale generated spec or SDK where ci spec checks one. [ci] enforce = ["spec"] makes a finding fail the job; "spec" is the only kind it accepts.

When the repository has a docs package, the site is built in the docs job and has no job of its own. That job has the gate's merged baseline, so the pages and a site_run hook can read the run's measured numbers. The site is built even when the docs check failed, so its result still reaches the verdict. The docs job starts after the check jobs, since each spec job uploads the routes executable and rustdoc JSON it built and the docs job merges them into its stores. A site_run hook that renders routes pages then compiles nothing.

Only run.yml runs these jobs. cargo soothfast init writes a workflow that calls it whenever the file configures one of them or [ci] pages. A cargo workspace with none keeps its test, gate and docs jobs in the workflow itself.

Deploying the site#

[ci] pages = true in the root soothfast.toml publishes the site to GitHub Pages on every push to the default branch. The docs job, which builds the site, uploads it as the Pages artifact. A second job in the caller, which calls the reusable pages.yml, then publishes the artifact. That job checks nothing out, runs no repository code and holds only pages: write and id-token: write, so no token that can write to the repository is involved. The deploy is its own workflow because a reusable workflow's permissions are checked before it starts: inside run.yml it would make every caller grant pages: write, with the setting on or off.

It needs three things: a [site] table, a docs package (the docs job is what builds the site), and the repository's Pages source set to "GitHub Actions". cargo soothfast init adds the pages job to the caller when the setting is on, and init --check reports the caller as drifted until it has been rerun. A failing docs check deploys nothing.

Keeping a trend#

[ci] trend_url = "https://owner.github.io/repo" keeps a performance trend with pages. The series is the trend.jsonl at the root of the published site, so the URL is both the opt-in and where to read it. On a push to the default branch, the docs job fetches that file, appends the point from the merged head baseline, and builds the series into the site it uploads. A rerun of the same commit replaces its point instead of adding a second one.

The first run finds no trend.jsonl (a 404) and starts the series. Any other answer, or a body that is not a JSON lines series, fails the job rather than publish a site without its history. A mistyped URL that returns a 404 reads as a first run and starts a new series, so check the first deploy's trend.jsonl. The URL must start with https://.

One verdict#

The reusable run.yml workflow gives a pull request one soothfast comment and one check, however many projects or shards it gates. Every gate job, the test job, the docs check and each check job records a result (project, kind, verdict, the last forty lines of output, reuse counts, seconds) and uploads it as soothfast-result-<name>. The verdict job downloads them all, runs cargo soothfast ci verdict, and posts one comment marked <!-- soothfast-verdict --> with a section per project, regressed and errored first, then advisory. Shards of one project fold into one section.

Each section keeps the output of its job without terminal colour codes, and without cargo's warning: blocks unless the job errored. A docs check that skipped its claims for lack of a measurement reads pass (claims not evaluated). run.yml sets CARGO_TERM_COLOR: never for every job.

Branch protection needs only the verdict check, named <caller job id> / verdict. The caller cargo soothfast init writes names its job soothfast, so a repo set up with init requires soothfast / verdict. The check fails when any project regressed or errored, or recorded no result; advisory findings do not fail it, and the summary line counts them apart (1 advisory). A perf-accepted label (soothfast:perf-accepted unless perf_accepted_labels renames it) applied by a writer waives regressions, never errors or docs drift.

Pull requests from forks#

The verdict body is also written to the run's job summary, whoever opened the pull request. A fork's run has a read-only token and no OIDC identity, so the verdict job cannot comment. It uploads only small data as the soothfast-verdict-comment-attempt-<attempt> artifact: the pull request number and what the plan expected of the run (the expected result names and the shard list), as plain text files. A second workflow renders the comment and posts it.

That workflow installs the same CLI as the verdict job, downloads the run's soothfast-result-* artifacts and runs the same ci verdict rendering over them, so the markup of the comment is produced by this repository's pinned code and not by anything the fork's workflow file wrote. The comment opens with a line linking the run and giving its conclusion, taken from the event. When the rendered verdict passes but the run did not succeed, a second line says so and asks the reader to read the run. A run that left no results gets a comment saying that.

The comment is posted as soothfast-bot, under the same marker, so the next verdict replaces it. The job runs in the soothfast-bot environment and sends the broker its OIDC token with the pull request number, the body and the head commit the run was for. The broker posts only for a workflow_run job in that environment on the default branch, and only while the pull request is open, from a fork, and still at that commit.

The head commit alone does not name a pull request, because two fork pull requests can share one. The job therefore also sends the id of the run it was triggered by. When the App holds Actions: Read-only, the broker reads that run and posts only if it is a pull_request run of this repository with the same head commit, head repository and head branch as the pull request. The reply says run_verified and the job logs a notice when it was not. Without the permission, or from an older action that sends no run id, the broker makes the checks above and nothing more, and the comment is still posted.

When the broker does not post (the App is not installed, the broker cannot be reached or refuses, the job has no OIDC token), the job posts with github.token instead, and a notice gives the broker's reason. It reads the pull request's head again first: a verdict for a commit the pull request has moved past is posted by neither. A pull request from the same repository is unaffected: its comment is posted directly and nothing is uploaded.

It is two workflows because the fork's own run executes code and a workflow file the fork controls. The comment job runs from workflow_run, which GitHub starts from the base repository with its permissions: cargo soothfast init writes it as soothfast-comment.yml, a caller of the reusable comment.yml with actions: read, contents: read (for soothfast.toml), id-token: write (for the broker) and pull-requests: write and nothing else. It never checks out or runs the pull request's code, and it runs only for a pull_request run whose head repository is not this one. The generated file carries a zizmor: ignore[dangerous-triggers] on its on: line for that reason.

Everything the fork's run uploaded is untrusted, so the job trusts only what GitHub reports about the run: its id, attempt, conclusion, head commit, head repository and head branch. The number in the artifact is posted to only when it is a plain integer naming an open pull request of this repository whose head is that commit, repository and branch, and whose head repository is not the base repository. Otherwise nothing is posted and a notice says why. Each expectation is a name of letters, digits and ._+- of at most 64 characters (a shard is I/N), with at most 256 names and 64 shards; anything else is dropped with a notice. Untrusted expectations can hide a missing section, which is why the run's conclusion is shown beside the verdict. The result files are read only when they total at most 20 MiB in at most 1000 files, and symbolic links, files with unusual names and results of a later attempt are removed first. The CLI shows a result's name in a code span, with any character outside letters, digits and ._-+/:# replaced by ?, shows a kind only when it is one it writes, and fences the result's text, so nothing in a result becomes a link, a mention or markup. Each attempt of a run uploads its own artifacts and the job reads none from an attempt later than the one that triggered it, so a re-run posts its own verdict or nothing, and a run for an older commit cannot overwrite a newer verdict. The job is stopped after 30 minutes.

The perf-accepted label is read with the job's own token, and counts only when a writer applied it. The label names come from soothfast.toml on the default branch, so a pull request into another branch uses the default branch's names.

A repository on the reusable workflow only needs the soothfast-comment.yml file; init --check reports it missing or changed like the main caller.

Bot landings#

A pull request the bot opens to land regenerated files runs no lane. cargo soothfast plan plans nothing for it, every lane job is skipped, and the verdict job still runs and passes, with one line in the comment saying no lane ran. The required check is a pass, not a skip, so the landing merges as soon as auto-merge sees it, with no ruleset bypass.

A pull request is a landing only when all of these hold:

  • Its author is <slug>[bot], where slug is soothfast-bot unless [bot] slug names another App. The actor of the run is not consulted: the bot is the actor when it updates or merges someone else's pull request.
  • Its head branch is in the repository itself and starts with bot/.
  • GitHub created and signed every commit on it for the bot (author the bot, committer web-flow, signature verified). action/land.sh commits that way through the API. A commit pushed to the branch does not qualify, whatever author it names. action/landing-commits.sh reads this from the API in the plan job.
  • Every file it changes against the base is one regeneration writes, or matches a [bot] landing_paths glob, and none is a soothfast.toml.

The files regeneration writes are CHANGELOG.md when the repository drafts one, each [[spec]] file with mode = "generate", everything under each [[sdk]] out directory, and each doc holding a capture block that ci capture covers. List anything else a job of your own lands through land.sh in landing_paths, including what a regen-run hook writes:

* and ? stay inside one path segment and ** crosses them. Anything else makes it an ordinary pull request that runs every lane: another author, a fork, a hand-pushed commit, one file outside the set, a diff or an API call that cannot be read. A landing that changes soothfast.toml is always ordinary, because the plan reads the pull request's own copy of the file and a widened landing_paths would otherwise approve itself.

A repository that would sooner skip pull requests for landings can make the App a bypass actor on the default branch and push to it directly. The bot's token can then write to the default branch unreviewed, which is why land.sh does not do it.

Carried lanes#

A lane is a unit of work a pull request may not need: rust:<package> (the bench build and gate of one package), import:<project> (the bench of a non-Rust project), check:<name> (one spec, proto, coverage, capture or site job) and docs (the docs check, with the site when it builds there). cargo soothfast plan drops the job of a lane the pull request does not touch and leaves its result to a stored pass, so a pull request that changed one container file pays for no build that would find nothing to do. The lane stays in the comment as pass (carried from <commit>), and the verdict still expects it.

A lane is carried only when a pass is stored under its key, which is its fingerprint and its delta. The delta is a digest of the merge-base blob of each changed file the lane reads, or absent for one the base lacks. It is empty when the pull request changed none of them, so a lane the pull request did not touch matches a pass of the default branch. A lane it did touch matches only a pass of an earlier head of the same pull request whose touched inputs began from the same base blobs. That head can be one the default branch was merged into: an update that leaves the lane's inputs and their base side as they were costs the lane nothing.

A fingerprint match alone is not enough. A pull request that reverts a lane's inputs to an older default-branch state matches an old pass while regressing against the current base, and a conflict resolved in the pull request's favour can leave the head's inputs identical while the base moved. The delta covers the base side of what the pull request touched. What it did not touch equals the base's by construction.

The fingerprint covers the lane's name, the whole root soothfast.toml, the soothfast version and revision of the checkout, the runner labels, the shard count, the Java and Node pins, the build variables the stores key on (RUSTC, RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER, CARGO_INCREMENTAL, RUSTFLAGS, CARGO_ENCODED_RUSTFLAGS), the [test] env values, and every file matching [ci] inputs. Then, by kind:

  • Rust lanes (rust:*, and the spec, proto and coverage checks): the files [test] selection sends to every package (files no package owns, Cargo.toml, Cargo.lock, toolchain and cargo config files, `[test] inputs`) and every file of the package and of each workspace package it reaches through a dependency of any kind, dev-dependencies included. A [test.packages.NAME] allow-list does not narrow this, and `[test] ignore` applies as it does to tests. The jobs install a floating stable, so the plan fetches the checksum of its release manifest (https://static.rust-lang.org/dist/channel-rust-stable.toml.sha256) and adds it.
  • import:*: the files in the project directory or matching its watch globs, its bench command, output, format, walltime and prefix, and the toolchain it runs on.
  • docs, and the capture check: the files of every Rust and import lane, the docs packages, and every markdown file. The site adds the files under [site] docs_dir and theme_dir, and a site with a site_run hook never carries.

[ci] inputs lists globs of files a lane reads that its own sources do not hold, such as a data file outside every package. A change to a match moves every lane:

The docs lane reads the gates' baselines, so the rust:*, import:* and docs lanes (and the site built with the docs) carry together or not at all. Tests are not lanes: they keep their own stored passes.

Every lane runs, and nothing is carried, when the run is a push or a bot landing, when the pull request carries soothfast:test-all, when the changed files are unknown, or when the lane has no fingerprint: no stored pass, cargo metadata failed, a package or path dependency lies outside the repository, or the soothfast revision or the stable channel is unknown. When the soothfast checkout is the repository itself, every revision is new, so the revision is replaced by a digest of the workspace members, action/, action.yml and run.yml.

A default-branch push and a pull request run each store a lane when every result it listed exists and is a plain pass, not carried, not claims not evaluated, and not a regression a label waived. The passes live in .soothfast/lanes, one small file per key, saved through the Actions cache under soothfast-lanes-<ref>-<run>-<attempt> and pruned to the newest 2048. A pull request's <ref> is its merge ref (<number>/merge), and GitHub scopes a cache a pull request creates to that ref: the base branch and other pull requests cannot restore it, so a pull request, fork or not, seeds passes only for itself. The plan job restores the pull request's entry, sets it aside, restores the base's newest entry (then the default branch's), and copies the first into the second without overwriting, so neither shadows the other. A pass the pull request stored is carried from its head commit, never from the merge commit.

A file no package owns (a container file, a workflow, a top-level script) is an input of every Rust lane unless [test] ignore lists it, so a repository gets the most from carrying by keeping [test] ignore accurate.

A fingerprint cannot see everything, and a lane carries a pass over these gaps: inputs outside the repository or fetched from the network, environment variables set only on the lane jobs, the runner image (only its labels are keyed), [patch] or cargo config paths outside the root, packages outside a lane's dependency closure that generate code for it, [docs] paths that name non-markdown files, a submodule's contents beyond its pinned commit, and edits to the caller workflow beyond the inputs the fingerprint names. List such files in [ci] inputs, or apply the soothfast:test-all label to run every lane on one pull request.

One command per job#

cargo soothfast ci <kind> runs one CI job: the flags, the choice of base and the verdict record that a workflow step would otherwise assemble in shell. It runs the same on a runner and on your machine. run.yml calls ci test, ci build, ci gate, ci gate-import, ci docs and ci verdict, and the action's regeneration is ci regen.

The run is read from the runner's environment (GITHUB_EVENT_NAME, the event payload, GITHUB_REF, RUNNER_TEMP). Where there is none, or to override it, three flags apply to every kind: --event pull_request|push|other, --base REF and --results DIR. Flags win. A job records its verdict as <name>.json in the results directory, $RUNNER_TEMP/soothfast-results on a runner, next to its output as <name>.log; without a results directory nothing is recorded, which is what a local run does. The exit code is the job's own.

ci test is the Test job of run.yml. On a pull request it runs cargo soothfast test --base the pull request's base commit, and on a push the previous head, both read from the event. A base that is unknown or is not in the checkout runs every package. --all runs every package and ignores stored passes. Features come from the test defaults of each package in soothfast.toml, and anything else is passed on to cargo soothfast test. With --project DIR it runs one project outside the workspace, always in full, taking --suite, --toolchain and --name (default test- and the directory). The record is named test-rust for the workspace, so its section of the pull request comment is the one the workflow writes.

ci gate is the gate job. With no -p it gates every package that has a soothfast bench target, each on its own, so its features and bench target come from that package's gate defaults in soothfast.toml. On a pull request it runs cargo soothfast gate --against-ref the base commit. On a push to the default branch it gates HEAD against its parent with SOOTHFAST_RECORD=1, which stores the run for later pull requests, and never fails; a HEAD with no parent lists each package's items as no-parent instead when --save-baseline names a baseline. A local run gates against --base, or leaves the reference to gate. --against REF gates against REF on any event. --shard I/N, --save-baseline NAME and --features F are passed on, and a shard records as PKG#I/N.

Each package records a rust verdict named for it, and the last 40 lines of every package's output are written to gate-comment.md in the results directory, with any run of three or more backticks spaced out so the output cannot close the comment's code fence. The exit code is 1 when a package regressed and 2 when one errored. --accepted LABEL turns a regression into a pass and adds a line to the comment naming the label, but never waives an error. Who may apply the label is for the workflow to decide before it passes the flag. ci docs is the Docs check job. It checks the [docs] packages, or the -p ones given, with the defaults each package resolves in soothfast.toml. On a pull request docs check compares against origin/ the base branch, and elsewhere in a run against HEAD^; a local run compares against nothing. --baselines DIR is where the gate legs' baselines were downloaded, one directory per leg: they are merged into the head baseline, which the check then reads. --expect-shards N is the shard count the gate ran with, and applies to pull requests only, since a push records in one leg. --plan FILE names the item listing the gate wrote. A run the gate does not measure on merges as not gated. When no gate measures the repository, claims are skipped and the output says so. When the merge fails, claims are skipped, binds and examples are still checked, and the job exits with the merge's code. Without --baselines nothing is merged and the check reads whatever baseline exists locally. The record is named docs. ci gate-import is the perf gate of a project outside the cargo workspace, the [[project]] tables with a benchmark command. It benches the head with the project's own command, benches the merge base of a pull request in a worktree of its own, and gates the imported results with gate --import. A push, or a run with no base, only benches the head. Each project is gated on its own, --project DIR picks one and --name renames its record (the ecosystem, plus the directory when two share one). Without --project every project runs and the exit code is the worst.

A head that fails or leaves no results errors the job, after the base is benched so the items it names are known. A base that fails or leaves no results has nothing to compare and passes. A regression exits 1 and an error anything else; the head's items are saved for the docs check unless the gate errored, and a pass that cannot save them errors. --accepted LABEL waives a regression, which then exits 0, and never an error. The worktree is removed whether or not the bench fails. ci spec is the spec checks of every package with a [[spec]] entry, or the -p ones given, with the spec defaults each package resolves in soothfast.toml. A package that generates a spec runs spec gen --check, which fails on a stale committed spec. On a pull request, and on any run given --base, spec gate compares with the base; a push alone has none. The base is the spec committed at the merge-base, which that same check pinned to its code, so nothing is built there; a committed spec that does not re-render is rebuilt in a worktree instead. The head's spec is always built from its routes. A package with a spec that is not generated runs spec check, and one with an [[sdk]] entry runs sdk gen --check. Every step runs even after one fails, and each package records a check verdict named spec-PKG with the worst exit code. A finding of spec gate or spec check does not count towards it unless [ci] enforce names spec: with nothing worse the record is advisory and the exit code is 0, and the last lines of the output name the step. With the bot input on, a pull request into the default branch and a push to it run neither spec gen --check nor sdk gen --check and print a line for each: that push's regeneration rewrites those files and the bot lands them. spec gate and spec check still run, and a package left with no step passes. Every other run keeps both checks: a pull request into another branch, a push to another branch, and a scheduled, manual or merge-queue run. So does a repository without the bot. The workflow turns this on by setting SOOTHFAST_REGEN=true. A workspace with no soothfast bench target keeps both checks: the regeneration runs in the gate job, which that workspace does not have. With nothing configured it says so and records nothing. ci proto runs spec check-proto for every package with a [[proto]] entry, or the -p ones given, which reconciles each message's fields against its Rust struct. Each package records a check verdict named proto-PKG. With nothing configured it says so and records nothing. ci coverage runs coverage report --check for every workspace member with a library target, or the -p ones given, whether or not the repo has bind markers. It reports every coverage dimension, and holds a package only to the minimums its configuration sets: coverage_min.DIMENSION in [docs] or [package.NAME.docs], and coverage for documented (see Per-package defaults). A dimension with no minimum is advisory: it is in the comment and never fails the run. A package that misses a minimum exits 1 and records an errored verdict, which no label waives. A package whose report could not be built, for lack of a rustdoc build for example, passes with coverage could not run: ERROR in its output when it sets no minimum, and exits 2 with an errored verdict when it sets one.

Each package records a check verdict named coverage-PKG, and the record carries the per-dimension figures (covered, total, percent and minimum). The comment shows them as one table above the sections, a row per package and a column per dimension, with (min N) where a minimum is set and not met beside one that failed. report render publishes the same figures as badges (see Reports).

The report needs a package's bench target only for the dimensions its benches and routes decide. A package whose bench executable is stored (from the gate or the prebuild lane) is read from it. Otherwise ci coverage does not build the bench unless the package sets a documented_strict, measured_declared, gated or specified minimum; measured (declared) then reads n/a and documented+, which counts claims through the bench's covers, is marked a lower bound (partial in the record). With no library target in the workspace it says so and records nothing.

tested and measured come from an instrumented build of the package's tests and bench target, which is slower than any other step. ci coverage runs it only for a package that sets a tested or measured minimum; every other package reads n/a (not run: no tested or measured minimum) and the run is neither started nor read from the store. The two follow their own minimums: a tested minimum starts only the test run, and a measured minimum only the bench run, which a package with no bench target does not have (measured is then n/a). A bench run that fails still yields a measured figure, recorded as a lower bound (partial) and not stored for later runs. specified applies to route and tool handlers, and every other item is n/a. ci capture runs docs capture --check for each docs package, or the -p ones given, which fails when the output recorded beside a capture block no longer matches what the block prints. A package with no capture block passes. A lone docs package is checked against every doc. Among several, the blocks of all the docs would compile into each package's crate, so only a package whose [package.NAME.docs] table names its own paths is checked. For a lone docs package, capture_paths under [ci] lists the docs to check in place of all of them, which leaves out a page whose output changes from run to run. On the default branch ci regen runs docs capture for the same packages and paths and lands the docs it changes. A package whose example fails is reported as a warning and its docs are left as committed; everything else still lands. [ci] skip = ["capture"] turns off both the check and the regeneration. Each package records a check verdict named capture-PKG. With no such package it says so and records nothing. With the bot input on, a pull request into the default branch and a push to it plan no capture check, and ci capture run there passes with a line saying the output is regenerated on the default branch. Every other run, a repository without the bot, and a workspace with no soothfast bench target keep the check, as with ci spec. ci site builds the docs site with docs build --out DIR, where DIR is target/soothfast-site unless --out says otherwise. It builds against the head baseline when .soothfast/baselines/head.json exists. It runs only when the root soothfast.toml has a [site] table; without one it says so and records nothing. The record is a check verdict named site.

A site whose pages are partly generated (an API reference, a perf report) names the command that generates them as site_run under [ci]:

ci site runs it with bash -euo pipefail from the workspace root before the build, under the same record, with $SOOTHFAST naming the running cargo-soothfast and $SOOTHFAST_BASELINE set to head when that baseline exists and empty otherwise. A command that fails stops the build. ci build LANE is the build-once job: it prebuilds into the stores what later jobs read, with cargo soothfast prebuild --only LANE for the bench, routes or rustdoc lane. With no package named, bench builds the gated packages, routes every package with a [[spec]] entry, and rustdoc the docs packages and every package that generates a spec. -p PKG names the packages of bench, --spec PKG[:TARGET] those of routes, and --docs PKG and --spec PKG those of rustdoc; naming any leaves the rest of the lane unbuilt, but for the changelog's packages on a push the bot regenerates. prebuild reads a spec package's target and features from its [package.NAME.spec] table and a docs package's features from [package.NAME.docs], unless :TARGET, --features or --docs-features says otherwise.

Without -p it builds the packages the lane applies to, found the way plan finds them: the benched packages for bench, the [docs] packages for rustdoc. routes needs its packages named, as PKG[:TARGET]. Packages that resolve the same soothfast.toml defaults share one prebuild call, and each set that resolves differently gets its own, in the order they first appear. On a pull request the call compares with the base commit, and --shards is the leg count the gate will read the stores with; on a push it builds one unsharded lane, comparing with the previous commit on the default branch. --stage is where the stores are copied for upload.

--plan-out adds each package's planned items to a plan file once the build is done, as baseline plan does, and a package that cannot be listed is skipped with a warning. --listing-out writes two lines, before DIGEST and after DIGEST, the checksum of the names and sizes of the files under .soothfast/bins when the job started and when it ended, so a job that saves the executables cache saves it when the two differ. The digest is the FNV-1a hash of the sorted name size lines in 16 hex digits, none when the directory does not exist, and ignores files ending in .tmp.

A build that fails is an error exit, not a regression. The remaining packages still build and the plan and listing are still written, and the exit code is that of the first failure. The job records no verdict. Bare ci does not run it, since it needs a lane. ci verdict folds the records in the results directory into the pull request comment and the run's verdict. --expect NAME:KIND names a job that must have recorded a result (a missing one errors the verdict), with KIND one of rust, import, docs, test or check. --accepted LABEL waives regressions, the way the perf-accepted label does, and never errors. The body is written to --out, by default verdict-comment.md in the results directory, and its job output stays inside the code fence. Posting it is left to the caller. A check record is a job whose every non-zero exit is an error, so nothing waives it.

ci regen is the regeneration a default-branch push lands. It measures every package with a soothfast bench target and regenerates CHANGELOG.md over the [changelog] packages, or those same packages when it names none (--no-changelog skips both), runs spec gen for each package with a mode = "generate" spec and sdk gen for each with [[sdk]], then docs capture for each docs package ci capture checks (it runs each capture block once, and the markdown holding one is what lands), then runs the REGEN_RUN command with $SOOTHFAST set when that variable is set (it needs REGEN_PATHS). It prints paths= and changed= lines, also written to --paths-out, and never commits or pushes. --baseline NAME names the baseline it measures into (default base).

When the latest tag is HEAD the changelog measures nothing for the release. Otherwise the tag's measurement comes from the run store (its own entry, or the run the gate recorded for that commit under the same conditions) before a worktree is built, and its API surface likewise. On a default-branch push the bot regenerates, ci build rustdoc also builds the public rustdoc of the changelog's packages under the features the changelog reads, whether or not --docs or --spec names packages, so the regeneration job finds HEAD's surface in the rustdoc store. One the docs already build under the same features is built once. --changelog PKG names the packages instead. A pull request never builds it, nor does a push with SOOTHFAST_REGEN unset; a repository that turns the changelog off with --no-changelog still pays for that build.

A push of the bot's own landing regenerates nothing: the bot authored every commit in it, every file it changed is one regeneration writes or matches a [bot] landing_paths glob or a REGEN_PATHS pathspec, and none is a soothfast.toml. A changelog carries measured numbers, and one that came out a digit different would otherwise land again, and that landing would regenerate again.

--probe regenerates nothing and prints generated=true or generated=false for that rule, then bot= and the bot's App slug (empty when soothfast.toml cannot be read). The action asks it first, so a push that needs no regeneration also skips the rustdoc toolchain install and every build that exists only for the regeneration. It does the same for a push that someone other than the bot has since followed on the default branch, which lands the regeneration from its own run. The action checks that again just before it regenerates, since the gate between the two can run long. Both fail open: without gh, a token or an answer, the push regenerates as it always has, and land.sh stays the final check before anything lands. The reference run is recorded either way.

The generated workflow runs the regeneration as a job of its own, Regenerate, after the gate. The gate job of a push only records the reference run. The regeneration job restores the built stores and the runs the gate saved, so measure reads HEAD's run back. It runs in one concurrency group per branch with cancel-in-progress: a newer push cancels an older regeneration still running, and a burst of merges runs one regeneration to completion. Two kinds of push never enter the group. The plan job runs ci regen --probe first, and the push of the bot's own landing skips the job, so it cannot cancel the regeneration of the push before it. A Regenerate (check) job then asks, once the gate has passed, whether someone other than the bot has pushed since. If so the job is skipped: an older push whose gate finishes late would otherwise cancel the newer push's regeneration and then find itself superseded. A newer push needs its whole plan, build and gate before it can enter, so the older one is in the group by then and is the one cancelled. The check fails open, like the two the action makes later: a script that cannot tell, or a check job that itself fails, reads as not superseded and the push regenerates.

The regeneration job compiles nothing the run already built. It waits for the Build (rustdoc) job and the spec check jobs, which stage their rustdoc and routes builds on a push that regenerates, whether or not the site needs them, and merges every soothfast-store-rustdoc and soothfast-store-spec-* artifact the way the docs job does. A build that failed or was skipped leaves nothing to download, and the job then builds for itself.

The last release is measured once. With head-runs, the action saves the regeneration's runs as soothfast-regen-runs-<branch>-<sha>-<attempt>. Before it regenerates, it restores the newest entry of that prefix and merges it with the runs the gate saved for the same commit. Only the regeneration writes that prefix, so a gate leg's save under soothfast-runs-<branch>- cannot shadow it, and a push that starts while an earlier regeneration is still running reads the newest finished one. The runs are saved even when a newer push cancels the regeneration or the step fails: each run is a file of its own, and a reader drops one that does not parse. A cache entry cannot be replaced, so the key names the attempt and a re-run saves what it measured as a new entry. Without head-runs the runs are saved under the commit's -regen key.

cargo soothfast ci with no kind runs every kind that applies to the event, in order, and stops at the first failure. verdict applies to pull requests and regen to pushes to the default branch.

The gate on its own#

The gate, with its comment and triage upload, is also a reusable workflow for callers that want it as a separate job or a matrix over packages:

soothfast_ref is the same tag or commit as in the uses: line, which the workflow cannot read for itself. Left empty, the scripts come from the commit GitHub reports for the workflow, and from the default branch with a warning when it reports none. cli-artifact names an artifact holding a prebuilt CLI at bin/cargo-soothfast from earlier in the same run; without it the workflow installs the release matching your Cargo.lock.
