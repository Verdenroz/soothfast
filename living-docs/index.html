Living docs#

Prose rots in two ways. It describes code that has since changed, or it states a number that is no longer true. The docs engine gates both, and this page is itself checked by the mechanism it describes.

Binds: prose tied to a fingerprint#

⌖scan·verified current

<!-- soothfast:bind path::to::item --> marks the prose that follows as a claim about that item's behavior. cargo soothfast docs accept records the item's current source fingerprint (FNV-1a over its source span, with ordinary comments stripped and whitespace normalized) in soothfast.lock. cargo soothfast docs check recomputes it and fails the build as soon as it no longer matches, which means the code changed under prose nobody re-read. Rewording a // comment inside the item leaves the fingerprint alone; a /// on a field does not, because that states part of the contract.

A marker the scanner cannot read is an error rather than a skipped line. That covers an unterminated marker, or one naming a kind other than bind or claim. Trailing whitespace after --> is fine. Dropping a malformed marker silently would report a green check for a claim nothing evaluated.

A bind can also name an inherent method or associated const of a public type, as crate::path::Type::method. Its fingerprint is the member's own span under the same rule. Trait impl methods are not addressable; bind the trait instead.

-p may repeat. A bind resolves against the package its first path segment names (- and _ are interchangeable), and a bind naming a crate that is not among the -p packages fails with a request to add it.

soothfast.lock is plain JSON: {"version": 2, "binds": {"item::path": "<16-hex-digit fingerprint>"}}. Running docs accept with explicit PATHS merges into the existing lock, so binds outside that scope survive.

A locked bind that no scanned page binds is an orphan. When the scan covers every [docs] paths page, docs check fails on each one and docs accept keeps them and prints how many; docs accept --allow-gone drops them. With PATHS, or with a package's own docs paths, neither reports orphans, since the bind may sit on a page that was not scanned, and --allow-gone is a usage error.

A lock written under an older version reports as needing one re-accept rather than as prose that drifted.

Binding code in other languages#

A target containing # is <path>#<symbol>: a symbol in a source file, with the path relative to the project root (the cargo workspace root, else the git toplevel, else the current directory). Java, Kotlin, Python, JavaScript, TypeScript and TSX files are supported, chosen by extension. Anything else is a Rust item path as above. File binds are parsed with tree-sitter, so docs check and docs accept need no cargo project and no -p; a repo whose binds are all file binds never builds rustdoc JSON.

docs check --binds-only runs the bind checks and skips claim evaluation and the generated-artifact check, so it needs no baseline and is the cheap check before a push. --skip-claims also needs none, but lists each claim as not evaluated.

Symbol names follow these rules:

  • Containers are dotted: Outer.Inner.method. A Kotlin companion object is the container Companion.
  • Overloads share one name, and the fingerprint covers all of them.
  • In Python, indentation is part of the code and counts toward the fingerprint. Ordinary comments do not, in any language; doc comments (/** */, docstrings) do, since the prose is bound to them.
  • A symbol inside code that does not parse is reported as missing, never guessed.

The lock key is the whole target string and the fingerprint is the symbol's own, so Rust binds and the soothfast.lock format are unchanged. Failures read unsupported language for PATH, file not found, or symbol not found in PATH; not locked and STALE behave as for Rust items. Claims are unchanged and still read the measurement baseline.

One block, several targets#

A bind may name several targets separated by whitespace, each a Rust item or a <path>#<symbol> file target. That is how prose about a feature spanning two languages gets one block that fails when either side moves.

The lock keeps one fingerprint per target, keyed by the target string, so a block with a single target locks exactly as before. docs check reports each target on its own line and names the one that moved; docs accept locks every target in the block.

Claims: numbers checked against a real run#

A claim marker looks like <!-- soothfast:claim item.backend.metric <op> value[unit] -->. The last two dot-separated parts before the operator are the backend and metric, and everything ahead of them is the item, so an imported id with dots or spaces (pytest::t.py::test_parse, vitest::src/a.bench.ts > sum > loop) works as written. Then comes one of < <= > >=, and a bound with an optional unit (ns ×1, us/µs ×1e3, ms ×1e6, s ×1e9). Unitless numbers are taken as-is, and underscores are allowed for readability, as in 25_000. docs check evaluates the expression against baseline["items"][item][backend][metric] and fails if the metric is missing or the comparison does not hold.

✓bench_claim_parse—p99 time 137 ns(limit < 2.0 µs)0limit 2.0 µs

Parsing one claim expression, the exact work docs check does per marker on this page, costs under 2µs at the tail.

A claim can also bound the difference of two items' metrics, which is how to state that one implementation stays within a margin of another, across languages included:

Each side is a full item.backend.metric. A - splits the claim only when both halves end in a known backend (perfcnt, walltime, alloc, asyncexec, callgrind, buildcost), trying split points from the right, so an imported id that contains - still reads as one item. The bound applies to the left value minus the right. A side with no measurement fails the claim and the message names it; a - with nothing after it fails to parse.

Coverage#

cargo soothfast coverage docs -p PKG and coverage measure -p PKG count the same public surface. It is every public item (functions, types, traits, constants, statics, modules and macros) and every inherent method, once each however many pub use paths spell it. Trait-impl methods and #[doc(hidden)] items are not counted, and neither are associated consts. coverage docs counts all of it; coverage measure counts only the callables, functions and methods. A minimum fails the run only when one is set, by --min or by coverage in [docs] or [package.NAME.docs].

cargo soothfast coverage report -p PKG [-p PKG ...] [--features F] [--json] [--check] [--executed] [--features-section] prints one row per item and a summary per dimension:

DimensionAn item is covered when
documentedits doc comment has text
documented+it is documented and its docs hold a fenced Rust example, or a soothfast:bind or soothfast:claim marker in the repo's tracked markdown names its path or a re-export of it; a claim names a bench, so it counts through that bench's covers (or the bench's own id), and only in a package with a bench target
testedthe package's tests, or those of a workspace crate it re-exports the item from, execute a line of it (doc tests are not instrumented)
measured (declared)a bench's covers names it, or the bench is the item; callables only, other items show n/a
measuredthe package's bench target executes a line of it, one pass over each bench
gateda bench in the gate's feature set declares it, through its covers or as the bench itself; callables only, other items show n/a
specifiedit is the handler of a route or tool, and the committed spec declares every one it serves and, for routes, a probe exercises it; every other item shows n/a

A fence counts as an example unless it names another language: no language, rust and rustdoc attributes such as no_run, ignore and compile_fail all count. measured (declared) reads what the benches declare; it does not check that the bench runs the item. tested and measured do: they build the package with -C instrument-coverage into their own target directory, run its tests and its bench target (one pass over each item), and credit an item when a counted region of the run shares a line with it. They cover functions, types and inherent methods; other items show n/a, as does measured for a package with no bench target.

That build is expensive, so a plain coverage report runs it only with --executed. Without the flag it reads the stored run for the tree as it is now, keyed on the package's files, those of every workspace crate it depends on, the workspace inputs, Cargo.lock, rustc -vV and the run, and prints (cached run from DATE) beside the figure so a reader knows it is not fresh. With no stored run, tested and measured read n/a (not run: pass --executed). A figure over several packages counts only those that ran; the summary then adds N package(s) not run and the figure is a lower bound. Only a run that finished is stored: a bench run that exits non-zero still yields a figure, but a lower bound (partial in the JSON, (partial) in the text, lower bound in its note) that is not kept, and a failing test run is an error. A registry soothfast-measure older than 0.9.0 in Cargo.lock has no setup exclusion, so measured also credits code only a bench's setup runs: it warns and marks the figure partial with an upper bound note. partial means the figure is not exact; its note gives the direction.

The report builds the package's bench under the gate's features ([gate] features, or [package.NAME.gate]), not the report's: a bench target with required-features exists only there. The bench's registry feeds measured (declared) and gated alike, so the two read the same set. An item is gated when a bench the gate runs declares it. Claims sharpen what the gate checks but do not widen what it measures, so they add nothing here. A covers that names no public item of the package prints warning: bench ID covers PATH, which is not a public item of PKG on stderr, from coverage report and coverage measure alike.

With --json, stdout is one object, items holding path, kind, documented, documented_strict, tested, measured_declared, measured, gated and specified per item, a features array with one coverage features object per package, and summary holding covered, total and pct per dimension. A dimension a tree cannot tell, such as documented+ for a non-Rust tree, is null, and the text report shows n/a.

coverage report also prints warning: fixture NAME in PATH is referenced by no bench of PKG on stderr for each #[soothfast::fixture] in the package's src and benches whose name appears nowhere else in those files, since a bench names its fixture in setup or setup_sized. It reads source text, so a mention in a comment counts as a reference. The warning is advisory.

With --check, the report prints only the per-dimension summary, then a line for each dimension below its configured minimum (coverage_min.DIMENSION, see gating), then one soothfast-coverage line holding the figures as JSON for ci coverage to record. It exits 1 when a minimum is not met, and 2 when the report could not be built and a minimum is set; with no minimum set it prints coverage could not run: ERROR and exits 0. A package with no minimum on documented_strict, measured_declared or gated reads a stored bench executable if there is one and never builds it; measured (declared), gated and specified are then n/a, and documented+ is a lower bound (its text carries claims not read, and partial is true in the figure). The instrumented run happens under --check only for a package with a tested or measured minimum; otherwise both are n/a, and a stored run is not read. Each column follows its own minimum: a tested minimum starts only the test run, a measured minimum only the bench run. --check --executed runs both.

A specified figure needs the package's spec files and a route listing. When either cannot be read the report prints a warning, shows specified as n/a and fails only if the package sets a specified minimum.

With --features-section, the report ends with the coverage features section for each package: how many public items sit outside the gate's feature set, per feature (a features array in --json). It is off by default because it costs up to three rustdoc builds per package, and a package whose section cannot be built is left out with a warning. See items the gate never compiles.

Coverage counts what the gate compiles: without --features it uses the package's features, else the gate's features for it.

Doc coverage outside Rust#

cargo soothfast coverage docs counts public symbols with a doc comment or docstring in Kotlin, Java, Python, JavaScript and TypeScript trees, with the same --min gate and --badge output as for Rust crates:

--lang takes a language (java, kotlin, python, javascript, typescript) or an ecosystem (gradle, maven, node), and --dir may repeat. With neither -p nor --dir, it reads the dir and ecosystem of each non-Rust [[project]] in soothfast.toml. Public means public in Java and Kotlin (Kotlin's default; private, internal and protected are not), export in JavaScript and TypeScript (including export { a, b as c } and export default a), and a name without a leading underscore in Python. Members count only when their container does. Trees named node_modules, build, target, dist, venv, test, tests or __tests__, and hidden directories, are skipped. coverage report --dir D --lang L prints the same symbols with documented only.

Items the gate never compiles#

Coverage is computed under one feature set, so a public item behind any other feature is missing from every denominator and no report says so. cargo soothfast coverage features lists the features of a package that its gate does not enable, with the number of public items behind each:

The gate's set is the one gate resolves for the package ([gate] features, [package.X.gate]), with the package's defaults on. The reference surface is a rustdoc build with --all-features; an item it has and the gate's surface lacks is outside the gate. Items are public functions, types and inherent methods, not trait-impl methods or #[doc(hidden)] items.

rustdoc records each item's #[cfg(feature = "...")], and an item also takes the features of the module, type or impl block around it. The features of a cfg that the gate does not enable get the credit, so under all(feature = "a", feature = "b") with a on, the item counts for b. An item gated on several features, as with any(..), counts under each, so the per-feature counts can sum to more than the outside total. An item gated by not(feature = "x") exists only while x is off, so a gate with x on misses it and --all-features does not have it either. A build with no features finds those; they are counted apart as off under a feature. An item whose cfg names no feature the parser can read, or whose gating sits on a private module that a pub use re-exports, is listed as (cfg not read), with a warning that names the rustdoc JSON format the parser was written for.

A package whose features cannot all be on at once (a compile_error! under --all-features) is measured one feature at a time instead: the gate's set plus that feature, one rustdoc run each, and the output says so.

The command reports and exits 0. --max-outside N fails it when more than N items are outside the gate.

Fence tags on rust code blocks#

tageffect
(none)becomes a real #[test], generated into the page's module of tests/soothfast_docs/
ignoreexcluded entirely: no test, no example, no check
no_runcompiled but never executed (a plain fn, not #[test])
capture-outputbecomes a block of the soothfast_capture example. docs capture runs it and splices real stdout into a text soothfast-output fence below it
feature=NAMEgates the generated test/example behind a cargo feature (comma-separated for a block that needs several to compile, no spaces — it is then gated behind all of them)
mock=NAME / mock=NAME(ARG)activates a #[soothfast::mock_seam] backend by name (requires an accompanying feature= tag)
covers=path::to::itemattaches a bind/claim's chip to this block instead of rendering it standalone (comma-separated for several items, no spaces)

cargo soothfast docs check -p PKG runs three checks in order: bind fingerprints against soothfast.lock, claims against --baseline, then a fresh generation of every test and example in memory, diffed against what is on disk. A stale docs gen-tests or docs capture run therefore fails CI just like a stale bind or a violated claim.

With ci regen on, a push to the default branch runs docs capture and lands the refreshed output. A failing example is a warning there, and the rest of the regeneration still lands. [ci] skip = ["capture"] opts out, and also drops the pull request check.

Which package#

docs check, docs accept, docs capture, docs gen-tests, docs reference, docs diff and docs routes take -p PKG. With no -p, they use [docs] package from soothfast.toml (a name or a list). gen-tests, capture, diff, reference and routes act on one package, so a list of several names is an error there and asks for -p. An explicit -p wins.

What gets scanned#

By default the docs commands read README.md and everything under docs/. [docs] paths in soothfast.toml replaces that scope: a list of files, directories and globs (*, ?, **) relative to the project root.

PATHS on the command line override the configured scope for that run. With no PATHS, docs check also lists tracked *.md files that carry binds or claims outside the scope and fails naming each one, since a marker no check reads would otherwise pass unnoticed. Add the file to paths, or pass it as a PATH. Pages generated by cargo soothfast are skipped.

Generated files#

cargo soothfast docs gen-tests -p PKG compiles a package's blocks into two targets, so a page adds a module rather than another binary to link:

  • tests/soothfast_docs/: one integration test, with a doc_<page>.rs module per page that has a testable block.
  • examples/soothfast_capture/: one example, with a block_<page>_<n>.rs module per capture-output block. It runs the block its first argument names: cargo run -p PKG --example soothfast_capture -- readme_1.

A capture block becomes a module, so it cannot use crate-level attributes (#![...], #[macro_use] extern crate), and crate:: in it names the example's root, not the block. A block that defines its own top-level fn main keeps it, whatever it returns. When a block's feature= tag is off, the example reports it as disabled, and docs capture skips it and keeps the output already recorded.

Every block of a package compiles into the same example, so one block that needs a feature it is not tagged with breaks docs capture for the whole package whenever that feature is off. Capture then builds the example first, reports one failure naming each block in the compiler's errors by its page and line, and runs nothing. Tag such a block with feature=.

The pages of a package share one test crate, and its capture blocks share one example crate. Anything crate-global in one block reaches the others: a #[macro_export] macro is visible to every block, a linkme registration lands in every block's registry, and two blocks installing a global allocator (directly or through soothfast::bench_main!()) cannot link. gen-tests rejects that last case, naming both blocks.

The generated main.rs files keep their mod lines and dispatch inside a verbatim! macro call. rustfmt leaves such a body alone and does not visit the modules it declares, so cargo fmt cannot change a generated file and fail docs check.

Every generated file starts with an @generated header and records the page it came from. gen-tests rewrites only files whose content changed and removes generated files nothing produces any more, including the per-page tests/soothfast_doc_*.rs and per-block examples/soothfast_capture_*.rs files of earlier releases. docs check fails while any of those remain. A file without the header is never touched.

The page paths given to a command assign pages to the package. A run with paths also keeps every page the package's generated files already record, so docs gen-tests -p PKG docs/one.md regenerates that page without dropping the others. A recorded page that was deleted, or has no blocks left, is dropped. To move a page to another package, delete its generated files and run gen-tests for both. A run without paths covers exactly the default scope.

Which blocks run#

A block that compiles is not a block that executes. cargo soothfast docs stats [PATH ...] [--json] reads the scanned pages and prints, for each, the rust blocks gen-tests turns into a running test (executed), the ones that only compile (compile-only: no_run, and ignore, compile_fail and the other rustdoc attributes, which gen-tests does not generate at all), and the page's bind and claim marker counts. A page with neither marker is flagged, since nothing ties its prose to code or a measurement. Capture blocks run in the capture example, so they are in neither count. The report is advisory and fails nothing.

Why this page has almost no ignored code#

Every rust block on this site either runs for real, with capture-output producing its output rather than someone typing it, or is at least checked to compile with no_run. An ignored block is invisible to all of the checks above and can drift silently for years. Reach for it only when a block genuinely cannot compile on its own, because it needs a real network or database, and prefer no_run even then if the code is otherwise real.
